## Context

项目当前是一个 TypeScript 开放 API 客户端，`api/index.ts` 统一导出各业务域函数、公共请求封装、配置、上传和轮询能力。现有测试覆盖请求构造和类型契约，但测试使用模拟请求，不适合作为真实接入示例。

本变更需要新增面向调用方的真实场景示例：代码应展示如何传入真实参数、如何依赖 `APP_KEY` / `APP_SECRET` / `OPEN_API_BASE_URL` 等环境变量、如何处理异步任务提交与轮询。示例不得在导入时自动执行，避免误触发真实接口。

## Goals / Non-Goals

**Goals:**

- 在 `examples/` 中提供每个公共函数一个真实调用场景。
- 示例覆盖同步查询、文件上传、异步任务提交、结果查询、轮询、配置读取和底层请求工具。
- 示例代码可被 TypeScript 静态检查验证，且不包含真实凭据或真实业务文件。
- 实现过程中不主动运行会访问真实开放 API 的示例或测试套件，执行权交给用户手动控制。

**Non-Goals:**

- 不修改现有 API 函数签名或请求路径。
- 不新增真实 API 集成测试，不把示例纳入自动测试运行。
- 不提供真实密钥、真实上传文件或业务数据。
- 不封装新的高层 SDK 行为。

## Decisions

- 使用 `examples/` 目录承载示例，而不是放入 `api/`。
  原因：示例是消费端代码，不应被 `api/index.ts` 导出，也不应混入客户端实现。备选方案是在测试文件中补充示例，但测试场景使用 fake fetch，无法表达真实调用。

- 每个公共函数对应一个具名示例函数，并默认只导出不执行。
  原因：用户希望“全部写完后一个个手动执行测试”，具名函数便于逐个调用；导入不执行可以避免误发真实请求。备选方案是单文件顺序执行所有示例，但这会违背手动逐个执行的要求。

- 示例通过环境变量和占位参数表达真实调用方式。
  原因：密钥和部分业务输入必须由用户本地提供，代码中只能保留安全占位值和说明。备选方案是内联示例密钥或固定业务文件路径，但存在泄密和误操作风险。

- 验证以静态类型检查为主，不主动执行示例。
  原因：示例会访问真实开放 API 或读取用户提供的文件，自动运行会产生业务副作用。备选方案是把示例写成自动化测试，但这与现有“测试无业务副作用”的约束冲突。

## Risks / Trade-offs

- 示例参数可能需要用户按真实业务调整 -> 在示例中使用清晰的占位常量和注释说明需要替换的位置。
- 公共函数列表未来变化后示例可能遗漏 -> 任务中要求对照 `api/index.ts` 的导出和各模块导出进行覆盖检查。
- 静态检查不能验证远端服务真实可用性 -> 明确远端调用由用户手动逐个执行，示例只保证调用方式和类型正确。
- 上传示例需要本地文件 -> 使用环境变量或显式占位路径，不提交真实业务文件。
