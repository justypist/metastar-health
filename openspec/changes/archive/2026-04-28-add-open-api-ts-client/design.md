## Context

项目当前只有基础 `package.json`、`.env.example` 和空的 `api/` 目录，没有既有 API 客户端实现。用户提供的开放 API 文档覆盖 10 类服务，其中 OCR、临床前文本提取、文献解析、靶点助手和靶点快速评估属于异步任务模式，其余接口为同步查询或搜索。

所有接口都需要 `x-app-key` 和 `x-app-secret` 认证头，密钥来自 `.env` 中的 `APP_KEY`、`APP_SECRET`。Node LTS 已支持直接运行 TypeScript，设计应尽量依赖 Node 内置能力，保持代码可直接使用和易维护。

## Goals / Non-Goals

**Goals:**

- 将文档中的全部 API 提供为 `api/` 下可导入的 TypeScript 函数。
- 抽取公共 Base URL、环境变量加载、认证头、请求封装、响应校验、上传文件和轮询能力。
- 用明确类型覆盖请求参数、统一响应、任务状态、搜索结果和主要业务对象，禁止使用 `any`。
- 按 API 领域拆分文件，保留统一导出入口，便于按需使用或整体导入。
- 支持 Node LTS 直接运行，避免非必要依赖。

**Non-Goals:**

- 不实现 CLI、Web UI 或交互式命令。
- 不保存或管理真实密钥，不修改 `.env.example` 当前变量语义。
- 不封装服务端未公开的接口，也不改变服务端响应结构。
- 不实现自动重试、缓存、限流队列或下载文件落盘，除非任务实现时发现最小可用性必须包含。

## Decisions

- 公共层放在 `api/client.ts`、`api/config.ts`、`api/types.ts`。
  选择原因：认证、Base URL、JSON 解析、错误处理和统一响应类型属于所有接口共享逻辑，集中维护可以避免每个 API 文件重复实现。备选方案是在每个文件内独立实现请求逻辑，但会增加不一致风险。

- 领域 API 按文档章节拆分文件。
  计划文件包括 `ocr.ts`、`text-extraction.ts`、`literature-process.ts`、`papers.ts`、`autocomplete.ts`、`target-assistant.ts`、`target-quick-assessment.ts`、`drugs.ts`、`hpa.ts`、`gbd.ts`，并通过 `api/index.ts` 统一导出。备选方案是单文件实现全部函数，但文件会过大，不利于维护和测试。

- 使用 Node 内置 `fetch` 作为请求执行器，并允许通过客户端选项注入 `fetch`。
  选择原因：Node LTS 已包含稳定 `fetch`，不需要额外 HTTP 依赖；注入能力可以让后续测试或调用方替换请求执行器。备选方案是引入 axios，但会增加依赖和响应包装差异。

- 文件上传函数接受文件路径、`Blob`、`File` 或二进制内容的最小通用输入，并在 Node 环境中优先支持路径。
  选择原因：当前使用场景是 Node 侧 TS 函数，路径是最常见调用方式；保留 Web 标准对象输入可以兼容更多运行环境。备选方案是只接受 `File`，但 Node 脚本调用会不方便。

- 异步服务同时提供 `submit*`、`get*Result` 和 `poll*Result` 函数。
  选择原因：文档明确采用提交/轮询模式，调用方既可能手动轮询，也可能需要一站式等待完成。备选方案是只提供底层提交和查询函数，但会让每个调用方重复实现超时、间隔和失败状态处理。

- 错误处理保留服务端原始响应信息，并在业务错误或 HTTP 非 2xx 时抛出自定义错误。
  选择原因：统一错误模型便于调用方捕获，同时保留 `statusCode`、`error`、`message`、`data` 有助于排查。备选方案是直接返回错误响应，但会让成功路径和失败路径混在一起。

## Risks / Trade-offs

- PDF 文档存在文本抽取中的换行或特殊字符干扰，可能导致路径拼写误差 → 以用户粘贴的完整解析文本为准，并在实现时集中列出端点常量进行人工核对。
- 服务端部分成功响应结构不完全一致，例如药物、HPA、GBD 的 `query` 和 `message` 在顶层 → 响应类型采用共享基础字段加接口特定泛型，不强行假设所有成功响应都只包含 `{ data, error }`。
- 文件上传在不同 Node 版本中的 `File`/`Blob` 支持略有差异 → 优先使用 Node LTS 支持的 Web API，并为路径输入封装转换逻辑。
- 类型覆盖全部深层字段会增加初始工作量 → 先覆盖文档明确字段和主要返回结构，未知扩展字段使用 `Record<string, unknown>` 表示，仍避免 `any`。
- 真实 API 调用依赖有效密钥和网络环境 → 实现阶段的验证以类型检查、无密钥错误路径和可替换 `fetch` 的单元级检查为主，真实联调作为可选步骤。
